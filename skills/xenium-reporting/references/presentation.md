# Xenium presentation production

Use this workflow for a new talk or a revision. Before drafting any slide, read
[slide text](slide-text.md); apply its completion check to the rendered wording,
including diagram text and footers. Read [template rebuilds](template-rebuild.md)
when a PPTX template is supplied or configured.

## 1. Establish the brief and account

Read the meeting context, project evidence and existing presentation source. Record
what listeners already know, what they should understand or decide afterwards, the
presenter's role, and the agreed scope, language, duration and template. Find the
requester's agenda and approved outline before proposing another one. Recover the
latest accepted corrections from the project record, including example choices,
visual treatment and ending. Carry those decisions into the working brief for a new
session; the original request alone may predate them. For a template-only rebuild,
retain the approved content and continue at assembly.

Check the latest correspondence and requester decisions for changes in responsibility
or meeting scope. A partner's new analysis can change what this presenter needs to
cover. Reconcile that change with the brief before polishing an obsolete account;
grant aims and available tools do not by themselves establish an agreed work plan.
Omit optional claims whose status remains unresolved. Keep unknowns that affect the
audience's interpretation or next decision explicit.

Write a short connected account before pagination. Start from a problem the audience
recognizes and its consequence, then introduce the evidence or method that addresses
it. Make the reason for each transition understandable from what listeners have
already seen. In a teaching talk, introduce terms before using them. Ground a new
method in a recognizable difficulty, its practical consequence and the change that
addresses it. The audience should be able to answer "why change what already works?"
from the example and explanation. Compare methods by their actual roles and show
how complementary tools combine. Present a useful approach on its own when a
comparison would require inventing an implausibly weak alternative.

Coverage belongs to the whole talk. A motivation, demonstration and implication can
unfold across pages. A local example or correction stays local unless it changes the
agreed purpose. Keep the main thread through revisions instead of promoting the most
recent comment into a new thesis. Respect the audience's competence: explain the
missing connection without turning the close into an unsolicited beginner exercise.

Keep the brief, accepted outline and consequential revision decisions with the
project's content source so another session can continue them. A review uses these
as its criteria, while remaining free to identify a flaw in the outline itself.

**Ready to design:** the account connects the audience's problem to a useful change
and the intended takeaway. Each section answers a question raised earlier or supplies
a needed premise; the ending fulfils the brief and latest accepted corrections.

### Data-status briefings

Put an overall status display before assay or method detail: what arrived, what has
the required inputs, what pairs across data types, and what is still waiting. Give
receipt scope from the source record; a few shared files do not define a cohort
fraction. Use recognizable sample/region identifiers and file types for confirmed
gaps, with exact paths in supporting material. Separate confirmed missing files from
questions for the sender. Keep received material, completed checks and proposals
visibly distinct.

Distinguish a tool's documented capability, a local trial, delivered outputs and
agreed future use. When its authors will present, focus this account on the local
evidence and use of their tools instead of repeating their methods presentation.

Select measures that answer audience questions, such as data volume, usable coverage
and information per cell. Preserve counting units and denominators. A consistency
check or favorable metric establishes only what it measured, not overall quality.
Unstable exploratory runs belong in supporting material unless they are the topic.

Describe transfer problems without assigning blame, credit collaborators' tools for
what they actually did, and frame proposals within the presenter's remit. Put internal
coordination in a private memo. A plan names the next useful work and its checks;
a timeline needs actual commitments. Ask only the questions that block that work and
that someone in the room can answer. Check correspondence before repeating an ask.

## 2. Choose displays and write the slides

Give each content page a point and a display that makes it understandable. Select the
layout for that explanatory job: a comparison, spatial image, workflow, timeline or
result table. Request missing or unsuitable scientific figures from
[Xenium figures](../../xenium-figures/SKILL.md), then consume its final exports.

A review of an existing deck includes display selection. Choose examples for the
decision they make understandable, using familiar, source-backed cases the presenter
can explain. Keep the required domain background proportionate to the talk's purpose.
An easy-to-cite trial is useful only if it illuminates that decision.

For a method demonstration, show a worked input, the relevant action and its visible
effect. When teaching construction, connect a small artifact or excerpt to the
decision it implements so listeners can adapt it. A component list establishes what
exists; a walkthrough needs to show what happens to a concrete object. Carry that
object across the explanation where useful. Retain scores when quantitative
performance is the question. When an observation stands for a larger dataset, state
its selection rule and show the relevant distribution or coverage. Identify
constructed teaching examples as illustrations of the mechanism.

Make hierarchy and change visible through position, grouping and selective emphasis.
Use arrows for an actual flow, dependency or change; use tables for comparison along
shared dimensions. Choose the display from the relationship to explain, rather than
filling a repeated card or step layout. For a progressive explanation, retain a common
diagram or visual object across pages and highlight the current part. Split competing
ideas into lighter pages before shrinking text. Count labels inside diagrams as part
of the audience's reading load.
A dense directory illustration can communicate accumulated complexity without asking
listeners to read every entry; a decision diagram needs readable labels and relations.

Sketch uncertain layouts before expensive figure work. Use existing approvals and
requested checkpoints; a sketch does not create a new approval requirement. Follow
[slide text](slide-text.md) for the words around the display. Allocate speaking time
by explanatory load; planned durations are estimates until rehearsed.

**Ready to review:** each explanatory display lets a listener locate the relation or
change being taught. A construction example contains an adaptable artifact. Read
adjacent pages together to confirm that each adds understanding, with its planned cues.

## 3. Check claims and audience understanding

Use one authoritative source for each number: the analysis table or a project record
regenerated from evidence. Keep its definition, counting unit, coverage and source.
Read it when revising a count. Reconcile apparently comparable numbers across pages
before deciding which are useful enough to display.
Check whether the counts describe the same population, assay and delivery scope.
A difference from a master inventory may represent unmeasured or unpaired material;
call it missing only when the delivery expectation and evidence establish that.
Keep the explanation of any displayed discrepancy in the cues or on the page when
it changes the result's meaning.

Review claims and comprehension separately:

- **Claims:** trace displayed statements and cues to measured evidence, a cited source
  or an explicitly identified inference/proposal. Check tool capabilities and newly
  added rationales against their sources. Resolve contradictions with the evidence.
- **Comprehension:** first read the pages in order using the audience's prior knowledge,
  without the author's rationale or cues. State the likely takeaway and question left
  by each section; locate where the talk answers it. Then read the cues to assess the
  delivered explanation and transitions. When essential reasoning exists only in the
  cues, give the page a visible anchor for it. Identify the exact phrase, missing
  example or relation behind a misunderstanding; "clear" or "too dense" alone is
  not a review finding. Distinguish a flawed plan from a poor execution of it.

When independent review is authorized and available, give the reviewer the brief,
current deck and relevant evidence without the author's defense of its choices.
Otherwise label the pass as self-review. Adjudicate suggestions against the brief
and sources; a reviewer suggestion is not itself evidence. Recheck affected claims
and transitions after substantive revisions, including wording added after an audit.

**Ready to build:** consequential claims trace to evidence, and the audience review
can retell the problem, the change and its benefit using the supplied pages and cues.
Resolve identified gaps in the artifact and recheck the affected sequence; an author's
explanation to the reviewer does not repair a missing explanation for the audience.

## 4. Assemble and iterate

Use the project's existing rebuild entry and runtime. With a configured template,
follow [template rebuilds](template-rebuild.md). Insert final figures whole and at
their aspect ratio, with editable slide text and tables around them. The figure task
owns artwork changes; the deck builder positions its new export.

Put lasting edits in the owning generator, content source or template profile. If a
content JSON is generated, editing only that JSON will be lost on regeneration.
Before rebuilding a deck the user edited in PowerPoint, reconcile their edits or
annotations with the source. Preserve the annotated original and build to a new path.
Locate the actual latest delivered file, including manual edits; the highest numbered
build or newest content JSON alone does not establish which deck the user finalized.

For each correction, identify whether it is a local exception or a general rule.
Sweep the general rule across the deck, including figures, captions and footers.
In the existing project revision record, map each applicable accepted correction to
the affected pages and its disposition: repaired, already satisfied or an explained
exception. Check the rendered result, not just the content source. Preserve settled
decisions while checking whether reordered or split pages still connect.

For first builds and changed layouts, check structure, content, notes and final-image
inclusion, then inspect the rendered pages at slide scale. View every changed page;
a geometry check can miss text wrapping into the next block. After a shared style
change, inspect all affected pages. Verify specified font sizes in the output's
units as well as the profile; a CSS-pixel value is not a point size. Use a contact
sheet to review rhythm and sequence, and full-size pages to judge reading and fit.
Provide that overview when the user is reviewing the deck remotely.

Keep titles, take-home lines and slide explanations as native text with ordinary
editable runs; scientific artwork stays in its final figure. In a custom teaching
diagram, embed labels needed to read its relationships; keep the slide's conclusion,
qualifications and surrounding explanation in native text. Inspect the diagram's
text as well as PPTX text boxes when checking this boundary. If editability is
requested or a user reports a failure, check the affected text and formatting in the
target application when available. XML structure alone cannot prove that the user
can select the intended phrase and change its formatting; report that limit when
application testing is unavailable.

**Ready to deliver:** the current source rebuilds the intended revision, affected
pages are legible, and claims and comprehension checks cover the latest content.
The accepted-correction review and the slide-text completion check have no unresolved
violations; explain any user-authorized exception or tooling limitation in the delivery.
Package checks establish file structure; rendering establishes visible fit; audience
review addresses usefulness. State separately whether native PowerPoint was tested.

## 5. Deliver the requested edition

Keep the presenter build, cues, final figures and regeneration inputs together in
the project. Before delivery, read the point of each page in order with its display
and walk through the cues against the available time.

For a sharing copy, select the main-talk pages in the content source and rebuild;
keep backups in the presenter edition unless the user wants them circulated. Make
the shared deck understandable without private cues. Use
[share_copy.py](../scripts/share_copy.py) with the existing Python environment's
`python-pptx` to remove speaker notes and set requested document properties. The
script preserves slides; it does not select or remove appendix pages. Use the
project's naming convention and a new output path, retaining earlier editions.

Check visible text, screenshots and document properties for audience-inappropriate
names, local paths and personal dates. Keep necessary attribution. Report the final
PPTX path, what changed and any limitation affecting use. An outline, figure bundle
or skill update does not complete a request for a PPTX.
