# Xenium 数据接收与分析输入检查：实施计划

## 目标与范围

新增 `xenium-data-intake`，将现有 `xenium-input-check` 改名为 `xenium-analysis-input-check`。名称以接收数据、在本方开展分析的研究者为视角。

设计、独立评审及用户批准后的实施和本地部署均已完成。新增接收模块、分析模块改名、聚焦测试和独立合成数据试用的结果见[执行证据](evidence/data-intake/README.md)。下文保留实施规格与设计依据；本次没有操作真实研究数据。

职责按所回答的问题划分。原生 Xenium 输出和整理后的 H5AD 都可以进入任一模块；“原始／处理后”“外部／内部”不作为模块边界。

## 1. 模块职责

| 模块 | 回答的问题 | 交付结果 |
|---|---|---|
| `xenium-data-intake` | 约定收到什么、实际收到什么、与指定来源相比还有哪些差异？ | 交付范围、文件清单、差异及证据覆盖范围；需要时起草一次集中补件请求。 |
| `xenium-analysis-input-check` | 收到的对象代表什么、内部信息是否对应、可以支持哪些分析？ | 矩阵、特征、细胞／样本标识、坐标与处理含义的检查，以及可用输入和限制。 |
| `xenium-biohpc-setup` | 本项目应使用什么工作区和运行环境？ | 复用现有 profile；仅在需要时补充配置。 |
| 下游分析模块 | 如何执行选定的分析？ | 各模块已有的方法、输入要求和结果。 |

两个检查模块独立可用。交付不完整时仍可检查现有矩阵；文件全部收到也可能存在细胞标识不匹配、坐标含义不明或生物学质量问题。整理后的交付包未包含约定范围之外的原生图像，不构成交付缺失。

路由示例：

- “下载全了吗？哪些文件缺了？”→ `xenium-data-intake`。
- “这个 H5AD 的 counts、细胞和坐标能否使用？”→ `xenium-analysis-input-check`。
- “接收数据并做基本 QC”→ 按需调用两者，共享已有清单与检查证据。
- 任一模块都不要求先确定完整分析方案，也不强制先运行另一个模块。

### 分析输入模块的最低流程

保留现有检查器与核心行为，并在改名后的说明中明确以下检查契约：

1. **解释表示形式。** 确认实际提供的对象、可读结构、矩阵及数据层角色；结合文档和元数据区分原始计数、归一化、变换值和未知含义。文件扩展名、层名或整数外观不足以证明语义。区分格式不支持、读取依赖不足和已确认的结构错误。
2. **核对索引和关联。** 检查矩阵轴、标签数量、适当样本范围内的标识符以及跨文件关联。分别处理同一 ID 集合顺序不同、ID 集合不同和跨样本重复 ID；不能凭相同行数直接关联，也不能把所有关系都要求为一对一。
3. **检查空间与样本边界。** 检查坐标的对象对应、有限值、单位和参考系，保留 slide、core、specimen 边界及生物学重复映射的已知和未知信息。缺少图像会限制特定工作，但不自动否定所有空间检查；未经验证的单位不足以支持距离解释。
4. **报告条件化的用途。** 说明已有结构支持的工作、需要语义确认的工作和被具体缺项阻塞的工作。区分元数据检查、抽样和全量数值检查，保留有效子集的结论，不给全包统一“分析就绪”标签。

以上是技能必须覆盖或说明未检查原因的内容，不代表检查器已自动实现全部检查。当前 checker 未覆盖的跨文件关联、坐标含义和生物学重复解释，继续由针对性检查与项目证据负责。改名不承诺增加新的格式读取器。

## 2. 数据接收流程

### 2.1 明确交付范围和比较基准

读取项目规则与已有 profile，确认用户指定的接收位置、可访问来源，以及交付是完整原生输出、整理后的导出包还是选定子集。优先复用已确认的信息。

分别记录三类依据：

1. **交付约定**：哪些样本、区域或文件原本应当提供；来自明确的请求、说明文档或发送方声明。
2. **来源清单**：某个位置实际列出了哪些文件；注明它是否覆盖交付约定，以及覆盖范围是否仅为发送方声明。
3. **格式参考**：在已确认的格式、版本和生成条件下解释组成要求；不自动成为本次交付约定。

来源清单本身可能已经有遗漏。与该清单一致，只能证明在该基准和覆盖范围内一致；不能自动证明所有预期数据都已交付。无法确认交付约定时先清点已授权位置，明确保留这一未知项。

约定“提供指定 MEX 路径”和“提供至少一种认可的矩阵表示”是两种要求，替代关系必须据约定判断。如果约定是“一个文件含三个 specimen”，文件存在不能证明内含对象齐全，应引用分析输入模块的结构证据或保留未知。证据相互冲突时明确呈现冲突，不默选方便完成检查的版本。

### 2.2 先做元数据清点

收集相对路径、文件类型、字节大小、枚举范围、排除项和读取错误。区分云端可见条目、本地占位文件和已实际下载的文件；不因清点而批量触发云文件下载。约定范围外的内容与扫描器因权限或实现限制跳过的内容分开记录，后者仍是未检查范围。

完整本地枚举、服务器清单和局部网页检查分别保留覆盖范围。局部网页观察不能合并成“已检查全部云端文件”。来源和账户使用用户指定或已授权的范围。

清单证据保留采集时段或其未知状态；这属于观察依据，不是 agent 文档的管理性时间戳。普通扫描不承诺原子快照，发现扫描期间变化时保留相关限制，不新增目录锁或快照系统。

### 2.3 比较文件并限定结论

以精确相对路径比较，分别报告缺失、多出和大小不同。文件数与总大小只作摘要；两者相等不代表文件对应。

“多出”仅表示相对于当前基准的差集，不自动表示不应交付。大小不同不能直接归因为传输损坏。不同包装层级需要明确指定比较根或映射，不自动剥离前缀、折叠大小写或改写名称来制造匹配。

将以下情况分开：

- 基准明确列出的文件在可完整检查的接收范围内不存在。
- 原生格式声明引用了某个文件，但该路径不存在。
- 依据常见输出结构怀疑有遗漏，尚需确认该文件是否在交付范围内。
- 目录无法读取、来源只列出部分内容或范围不明，无法判断。

`experiment.xenium` 的声明和格式结构可提供具体检查线索；通用原生输出惯例不能直接套到整理后的导出包。

### 2.4 分开记录交付差异和分析影响

例如：

- 承诺提供的 MEX 文件缺失，即使 H5 存在，仍是交付差异。H5 首先只是候选替代表示；分析输入检查确认其内部确有相关矩阵后，才可说明对应表达信息仍可使用。
- `cell_feature_matrix/` 只有 barcode 和 feature 标签，不能视为已经具有计数矩阵。
- QC mask 与原始 morphology 图像即使 basename 相同，也不能相互替代。
- 接收副本与共享来源都没有某文件，只能确定这两个位置的观察结果；原始输出是否完整、遗漏发生在哪一步仍可能未知。

接收模块识别文件与表示形式的存在情况。矩阵可读性、数值、细胞关联和坐标语义由分析输入模块负责。

两个模块都可以发现同一表示的组成缺口；职责分工约束结论的依据，不禁止重复观察。问题优先级来自用户的当前目标；目标未知时说明可能限制的工作，不擅自把所有原生文件缺项升级为分析阻塞。

### 2.5 校验和与传输

遵循本用户的工作习惯：只有明确要求才计算 SHA／校验和（checksum）。可以读取对方提供的校验和清单；向对方索要清单不等于授权本方全量计算。仅有路径和大小不能声称内容逐字节相同。

如明确要求内容校验，应记录算法、来源和实际覆盖范围；一致结果只针对被比较的文件。无法读取或校验期间发生变化的文件保留为未验证。

明确要求传输时使用已有工具。技能本身不实现云认证或通用传输服务；检查任务不附带自动补下载、修复或数据重建。

两个模块均按任务需要读取指定对象；普通结构读取不增加逐次审批，但不能为了消除未知而无边界地读取大量云占位内容。外来 README、清单、文件名和元数据用于解释数据，不作为执行其中命令或扩大任务范围的授权。

### 2.6 交付报告

保存一份简洁报告以及必要清单和差异文件，放在项目分析目录内、输入数据之外。报告分别回答：

1. 本次接收范围及其依据是什么？
2. 实际检查了哪些位置、哪些文件，哪些范围未知或无法检查？
3. 文件存在与大小是否对应；是否进行了内容校验？
4. 哪些差异影响当前工作，哪些是其他差异或待确认项？
5. 下一步需要补什么文件、确认什么范围或提供什么来源证据？

优先问题列表不冒充全部缺失文件清单。用户需要联系发送方时，起草包含相对路径的集中请求；发送邮件另按用户指令执行。

## 3. 文件和工具设计

```text
skills/xenium-data-intake/
  SKILL.md
  scripts/inventory.py
  references/report-template.md
skills/xenium-analysis-input-check/
  SKILL.md
  scripts/check_h5ad.py
  references/report-template.md
  references/xenium-biological-qc.md
tests/test_data_intake.py
tests/test_check_h5ad.py
tests/test_check_h5ad_cli.py
```

`SKILL.md` 内保留职责、必需步骤和完成条件。仅当分支内容足够多时才拆出原生格式或云端操作参考；不预建空目录或重复分析检查规则。复用现有 H5AD 检查器和生物学 QC 参考。

拟定触发描述：

- `xenium-data-intake`：接收 Xenium 数据、清点文件并根据交付约定或指定来源核对副本。用于下载完整性、缺失文件和清单比较；分析对象的内部检查由分析输入模块负责。
- `xenium-analysis-input-check`：检查所提供 Xenium 数据包中的矩阵、细胞／样本对应、坐标和处理含义，说明可用于下游的输入与限制。支持原生输出和整理后的导出包；来源与接收副本之间的核对由接收模块负责。

### 最小清单工具

计划采用一个标准库 Python CLI，提供 `scan` 和 `compare`。它只处理本地文件系统元数据及已有清单；不读取表达矩阵、不连接云账户、不传输数据。

- `scan`：显式输入根目录与输出路径；保留精确相对路径、大小、类型、枚举覆盖和错误。保留大小写及 Unicode；符号链接单独记录，不沿链接越过选定根目录；压缩包默认作为一个文件。
- `compare`：显式指定基准清单与接收清单，以路径而非总数比较。同一路径两端均有记录时可比较类型和大小；类型不同单列。
- 首版工具保守地按整个选定范围判断覆盖：接收清单完整时才能确认基准条目“缺失”；来源清单完整时才能确认接收条目“相对基准多出”。否则记为“仅一端观察到／待确认”。排除项不兼容时不给出全量结论；暂不实现复杂的子目录覆盖推理。技能仍可引用独立、完整的子目录清单形成局部结论，不抹去已成立的局部证据。
- 清单共同读写一个版本化 JSON 格式，最小字段为 `schema_version`、来源／根目录标识、观察时段、选定范围与约定排除项、`enumeration`（完整／局部）、扫描跳过项、`entries`（相对路径、类型、字节大小、可用状态）和 `errors`。未知可用状态显式保留；字节大小仅适用于文件。拒绝重复或不合法路径及不支持的版本。
- 工具区分完整运行、部分运行和无法运行；保留部分结果及错误，不能把失败后的空列表写成空目录。差异数量独立于运行状态：完整运行仍可能发现差异，部分运行仍可能发现可靠的类型或大小差异。CLI 与机器结果均需让调用者识别这三类运行结果。
- 输入只读；结果保存在输入之外，默认不覆盖已有输出。零字节文件作为观察项，不能自动判成损坏。
- 元数据为默认模式；云占位状态只在有可靠平台信息时标注，否则为未知。常规 `stat` 不能证明文件内容已物化。

首版只实现 `scan`／`compare` 及上述自有 JSON 格式，不实现本方哈希计算、云接口或任意第三方清单解析。外来清单可以作为人工核对证据；需转换时保留原文件和转换说明，不伪装成完整的直接枚举。显式要求内容校验时使用适用的已有工具，并在报告中说明覆盖。检查报告沿用 Markdown。

项目产物使用所在项目的文件命名规则，包括日期标签；不新增全局登记表、项目脚手架或管理性时间戳。具体项目路径和研究发现保留在项目内，不写入可复用技能。

## 4. 改名与迁移

本地检查发现，旧技能经由 skillshelf 链接在使用；直接移动源码目录会使现有部署链接失效。现有 H5AD 检查器还有未提交修改，CLI 测试也未提交，实施时必须保留。

1. **记录受影响文件状态。** 检查差异和未跟踪文件，保留现有工作，不做 reset、clean 或全局字符串替换。
2. **迁移分析输入模块。** 保留检查器及参考文件，更新目录名、frontmatter、标题和报告标签。此次改名保持 CLI 参数与机器可读结果契约。当前技能已经限制在一个包内，未提供自动传输或补件行为；保留其包内 sender evidence 复用与语义追问，将来源间完整性比较明确交给接收模块。旧文案中的“file identity”按实际证据描述，不升级为默认哈希。
3. **更新当前入口。** 修改 router、README 模块表及部署示例、AGENTS 职责表和两个 H5AD 测试中的脚本路径；检查 composition、QUICHE 的现行入口措辞。
4. **保留独立身份。** BioHPC 上已有 `xenium-input-check` 环境、module 名和项目运行路径不随技能名更改。历史报告、旧命令和试验记录保留原意，通过迁移说明解释名称变化。
5. **处理旧入口。** 因旧名称已经部署，迁移时在旧源码目录暂留一个仅供旧名称显式调用的薄转发 `SKILL.md`，与目录迁移一并完成；只转到新模块，不复制分析逻辑。只有发现仍在调用旧脚本路径的实际消费者时才增加 CLI wrapper。当前文档和 router 统一使用新名字。
6. **单独部署。** 部署阶段使用 skillshelf CLI 检查注册、注册新名称并验证资源解析，再撤下旧入口。用 `skl where ... --json` 确认实际目标，不手改管理器元数据。

兼容入口的退出条件已满足：新入口部署和资源验证完成，已知消费者已更新，旧 Codex 部署已撤下，旧 skillshelf 条目已可逆退役。源码中仅保留不参与当前路由的薄转发，使退役库链接仍可解析和恢复；没有保留第二份分析逻辑。撤下前已通过实际部署路径验证转发和参考文件可达。

干净 checkout 应能从 README 到达所有必要资源；不依赖作者个人 profile 或其他独立安装的技能。

## 5. 验证与验收

| 场景 | 必须观察到的行为 |
|---|---|
| 约定只交付 README + H5AD，没有原生图像 | 不因缺少原生图像判定交付缺失；H5AD 内容有效性仍需独立检查。 |
| 原生包没有任何表达矩阵表示 | 列出具有依据的具体缺口；不自动重建、过滤或修复数据。 |
| 两边文件数相同，但路径不同 | 找到缺失与多出的路径，不能给出完整结论。 |
| 承诺的 MEX 缺失，H5 存在 | 分开描述交付差异和表达信息是否仍可用。 |
| 只有矩阵标签，或只有同名 QC mask | 不能误判 counts 或原始图像存在。 |
| 本地与服务器一致，只查看过部分云端目录 | 保留每个位置的覆盖范围与原始来源未知项。 |
| 占位文件、无法读取的目录或部分清单 | 不隐式批量下载；未知不写成缺失或完整。 |
| 文件全部到齐，但细胞标识不匹配 | 接收与分析输入模块得出各自有依据的结论。 |
| 有对方的 SHA 清单，但未要求本方计算 | 不运行本方哈希；内容一致性仍标为未验证。 |
| 用户要求接收并做基础检查 | 路由到需要的模块一次，复用证据，不强制完整分析规划。 |
| 改名后的技能与旧入口 | 当前路径和必要资源可解析；兼容策略具有实际验证证据。 |

将关键场景落实为包含“输入证据、预期结论、不得发生的动作”的试验记录，至少增加以下反例：

- 同一 H5AD 分别配以明确范围、未知范围、包含额外对象的约定：分别得到范围内核对、有限清点、具体缺口；不自动补下载。
- 同路径、同大小但不同字节的合成文件，且未要求哈希：只能报告元数据相符，不读取全文件来证明内容一致。
- H5 候选存在但缺少相关矩阵：仍保留表达信息缺口，不以扩展名消除问题。
- 同 ID 集合不同顺序、同数量不同 ID、跨 specimen 重复 ID：按键与样本作用域得出不同结论，不按行号硬关联或静默重写文件。
- 不可读目录返回零条记录、扫描器跳过目录、交付说明相互冲突：分别保留错误、覆盖缺口和冲突，不能输出“空目录”或“完整交付”。
- 文件已到但一个约定的 specimen 未在对象内确认：接收报告引用结构证据或标明内含对象覆盖未知，不只按文件数验收。

工具测试覆盖路径比较、相同总数但不同内容清单、部分枚举的双向判定、类型差异、读取错误、重复／非法路径、输出保护和符号链接边界。首版不测试未实现的哈希功能；校验和场景验证的是 agent 不擅自计算的行为。

运行 `git diff --check`、技能名／frontmatter 检查和仓库相对链接检查。迁移后运行两个现有 H5AD 测试及新清单工具测试，区分原有失败与本次引入的失败。

路由和语义边界还需要独立的代表性 agent 试用，覆盖上表中的关键分歧；使用合成或明确限定的输入，不把预期答案提供给被评估对象。记录实际动作、输出、失败和限制到既有 `docs/skill-trials.md`。静态链接检查和同行赞同不能代替行为验证。

验收完成意味着：新名称到达正确职责；当前路径和旧入口迁移结果明确；局部检查不会被写成全量完整；原有分析检查行为保持；项目证据与可复用规则分开保存。

## 6. 实施顺序与完成条件

| 阶段 | 工作 | 完成条件 |
|---|---|---|
| A. 设计收敛 | 完成本计划与独立评审，决定首版工具范围和迁移策略 | 关键边界与评审处置明确，可直接实施。 |
| B. 接收模块 | 编写 SKILL、报告模板与最小清单工具 | 有独立入口和可复现的清单／差异证据。 |
| C. 分析模块改名 | 移动已有实现，更新当前引用，保留现有修改及兼容入口 | 新旧入口按计划解析，运行环境和历史证据未被误改。 |
| D. 路由及验证 | 更新入口说明，运行聚焦测试和代表性试用 | 测试结果和行为证据可复查，失败已处理或明确限定。 |
| E. 部署与交付 | 按部署请求更新 skillshelf 并核对链接 | 新入口实际可用后再撤旧入口；报告最终 diff 和验证范围。 |

实现过程中如发现需要新增分析行为，应作为单独变更说明，避免在改名中夹带检查逻辑重写。本次无需访问 BioHPC 或真实研究数据来完成设计和迁移验证。

## 7. 独立评审

评审由另一个模型独立完成。发送的是不含源码、仓库路径、机构／合作者身份、研究数据和运行配置的通用设计。评审范围为职责划分、证据语义、工具必要性、迁移原则和验证设计；本地实际入口与改动状态另行检查。

评审的原始结论：

> 我的判断是：修改后可以进入首版实现，但不应把当前文字原样作为开发和验收的最终规格。

> 最需要收紧的三个词是“完整”“一致”和“可分析”：每次使用，都应说明相对于什么约定、覆盖了什么证据，以及在哪些条件下成立。

完整回复保存在 [data-intake-review.md](data-intake-review.md)。它评审的是发送时的通用方案，没有读取现有仓库，也没有再次评审本修订稿。

本计划采纳的实质修改：

- 分开交付约定、比较基准和格式参考；补上表示替代与容器内 specimen 覆盖的问题。
- 明确完整、局部、未检查、失败及本地可用性的差别；约定排除和扫描跳过分别记录。
- 补齐分析输入模块的最低流程，限定 H5 候选与已确认可用表示的区别，保留检查深度。
- 首版工具限于一种 JSON 证据格式及 `scan`／`compare`；不增加哈希、云适配或归档展开。
- 根据实际旧部署保留临时转发，明确退出条件，并验证资源加载。
- 把代表性验收改为可判定的证据、结论和动作断言，增加同大小不同内容等反例。

保留的工程取舍：评审建议覆盖判断可以细到子树；首版比较器先采用整个选定范围的保守判定，通过独立子目录清单支持已确认的局部结论，暂不实现通用覆盖推理。评审未看到现有分析技能，所以“补齐最低流程”主要是让本计划写明已有契约及其边界，不意味着重写检查器。

作者判断：上述修改使本计划可以进入受限首版实施。该判断基于设计收敛与本地入口检查；没有把同行赞同当作实现或运行验证。
