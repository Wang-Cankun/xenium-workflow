# 外部模型对 Xenium 技能拆分计划的原始评审

[修订后的实施计划](data-intake-plan.md)

评审输入为通用设计，未包含仓库源码、路径、运行配置、机构／合作者身份或研究数据。回复针对送审版本；没有再次评审修订后的计划。

以下原始回复未作改写。

---

总体结论

我的判断是：修改后可以进入首版实现，但不应把当前文字原样作为开发和验收的最终规格。

两个名称和基本分工值得保留。xenium-data-intake 关注交付约定、收到的对象以及相对于特定基准的差异；xenium-analysis-input-check 关注这些对象的含义、结构对应关系和用途限制。这比按照 native versus processed 划分职责合理，也避免把“文件全部收到”误当成“适合所有分析”。

当前主要问题不是功能不足，而是若干结论的成立条件还不够明确：什么决定应当交付的范围；清单比对究竟证明了什么；部分枚举如何影响缺失判断；第二个技能至少检查什么；以及重命名究竟承诺哪一种兼容。这些需要在实现前补齐，但不需要因此扩展成一套大型数据管理平台。

一、必须修正：把交付约定、比对基准和格式参考分开

提案中“从用户请求、source manifest、文档或 native-output references 建立范围”过于宽泛。这些材料可以提供不同种类的证据，但不能默认具有相同权威性。

交付约定回答“这次承诺交付什么”。它可能规定具体路径，也可能规定某种表示、某些 specimen，或者明确限定为一个 curated export。

比对基准回答“这次拿什么与接收端比较”。一个 sender manifest 可以是某次源目录扫描的结果，但它不一定说明扫描是否覆盖了全部源数据，也不一定等于双方约定的完整交付范围。

格式参考回答“在某种已声明的格式、版本和生成条件下，通常应如何理解这些对象”。它不能未经确认就升级为本次交付的强制文件清单。

同一份 manifest 可以同时承担前两种角色，但必须有明确声明，不能因为文件名叫 manifest 就自动获得“完整交付真相”的地位。

建议把 A 改为：

“分别记录交付约定与比对基准，包括各自的来源、适用范围和已知限制。格式文档只在适用条件明确时辅助解释要求。若约定不明或材料冲突，则继续执行能够成立的清点与局部检查，但不作完整交付结论。”

这里还需要区分两种要求：“必须收到某个 MEX 文件”与“必须收到至少一种约定认可的表达矩阵表示”。前者不能被 H5 自动满足；后者则可能允许替代。不能先把所有要求都变成路径，再在发现缺件时凭直觉放宽要求。

还有一个容易遗漏的边界：交付约定未必能完全用路径表达。例如，约定是“一个文件包含三个 specimen”，路径和尺寸检查只能确认容器文件存在，不能证明三个 specimen 均在其中。这部分应由结构检查提供证据，或者明确保留为“内含对象覆盖尚未核实”，不能因为文件到齐就宣称整个约定已经满足。

二、必须修正：让每一种结论都受证据覆盖范围约束

提案已经反对用相同文件数证明完整性，但还需要进一步明确：相同路径和相同尺寸也只证明清单层面的相符，不证明字节内容一致。

建议报告至少分别说明：交付范围是否明确、枚举覆盖是否完整、路径与尺寸比对结果、本地内容可用性，以及是否执行了内容校验。它们是不同结论维度，不必为此建立复杂状态机，但不能压成一个 verified=true。

其中最重要的规则是“未观察到”与“确认缺失”不能混用。

如果某个承诺路径所在的目标子树没有成功枚举，那么没有看到该路径只能记为未观察到或无法判定。若该子树已完整枚举且路径不存在，则可以确认缺失。其他不相关子树的失败，不必抹去这条已经成立的局部证据。

反过来，如果源清单只有部分覆盖，目标端出现一个不在清单里的文件，可以说它“不在当前基准中”，但未必能说它是“不应交付的额外文件”。数学上的清单差集和交付语义上的异常，不是同一回事。

排除项也必须分开。约定明确排除的内容，本来就不属于交付要求；扫描器因性能、权限或实现限制跳过的内容，则仍然是未核验范围。不能通过把错误或未检查目录记为 exclusions，就把部分扫描包装成完整扫描。

还应明确以下几条报告规则：

尺寸相同不写成“文件内容相同”；尺寸不同不直接归因于传输损坏，因为仅凭这些证据不能确定差异发生在哪个阶段。文件与目录的类型冲突需要单独报告，目录的尺寸不能用于证明其内部内容相同。占位对象显示出路径和逻辑尺寸，也不能证明对应内容已经下载到本地。

每份库存证据应保留清晰的 source/destination 标识、比较根的定义、采集时间或未知状态、枚举覆盖和错误。不同包装层级之间的路径映射应显式说明，不能为了得到“匹配”而自动剥离目录前缀、折叠大小写或改写名称。

不需要为首版实现原子快照、目录锁或复杂取证功能。记录观察时段，并在已观察到文件变化时降低结论强度即可。重要的是不把一次普通目录扫描说成冻结后的完整快照。

三、必须修正：补齐第二个技能的最低检查流程，并收紧双方的解释权限

当前 intake 有 A–F 的流程，而 analysis-input 主要只有职责说明。这不足以约束一个可复用技能的行为。

“保留现有行为”不能替代新技能的最低规范。即使已有实现，也应明确哪些检查属于这个新名称所承诺的能力，哪些只是旧流程的偶然行为。

我建议 xenium-analysis-input-check 的首版至少覆盖四方面。

表示含义：识别提供了哪些对象，尝试读取其结构，区分主矩阵、其他数据层和外部元数据的角色。原始计数、归一化值、变换后的数值或者含义未知，应按证据分别说明，不能只根据文件扩展名、层名或数值看起来像整数就认定其语义。无法支持的格式、缺少读取依赖和可确认的结构损坏，也应分开报告。

索引及关联：检查矩阵轴、标签数量、标识符、命名空间、关联基数和顺序是否相容。相同行数不是正确 join 的证明；相同 ID 集合但顺序不同，也不等于无法使用。唯一性应按声明的键判断，例如 specimen 内唯一与全局唯一不是同一个要求。一对一、一对多关系也应根据表示含义判断，不能把所有关联都硬编码为一对一。

空间结构：检查坐标属于什么对象、能否对应相关 cell 或其他实体，以及单位、坐标轴、参考系和图像关联是否有依据。没有单位或参考系时应保留未知，不应凭数值范围猜测后宣称可正确叠加。没有图像不等于所有空间工作都不成立，但确实可能限制图像配准或形态学相关工作。

能力结论：说明哪些工作已有足够的输入结构支持，哪些需要额外语义确认，哪些被明确缺项阻塞。没有固定分析计划时，仍可检查明显结构问题；但此时应输出有条件的能力说明，而不是一个泛化的“分析就绪”结论。

这些检查都应标明实际检查深度。只读取了结构和元数据，不应声称检查过全部矩阵数值；只检查了部分对象，不应把结论推广到整个包。也不应为了获得更强结论而默认展开所有大数组或执行完整下游分析。

双方职责不应定义为“谁独占哪些文件”，而应定义为“谁负责哪类结论”。analysis-input 可以独立发现组成某个表示的必要文件缺失；intake 也可以观察到明显的组成缺口。这不构成职责冲突。

真正需要收紧的是 intake 的语义推断。例如，“H5 文件存在”应先表述为发现替代表达表示的候选，不能在未检查内部结构时直接写成“表达信息仍然可用”。同理，名称像 morphology 的 QC mask 不能满足图像要求；无法可靠识别角色时，应记为未确认，而不是为了完成清单而强行归类。

“紧急缺失的分析输入”也需要条件。其紧急性应来自用户声明的工作目标，或已经明确的必要能力。目标未知时，更合适的表述是“该缺项可能限制某类工作”，而不是把某套 native 文件清单中的所有缺项都升级为分析阻塞。

四、必须修正：权限边界要贯穿读取行为，而不只是限制显式传输命令

校验和的显式授权要求应保留，而且不能因“发现可疑差异”“对方附了 checksum manifest”或“用户希望检查完整性”而自动升级为本地摘要扫描。

读取 supplied checksum list 与验证接收端内容是两件事。没有本地计算时，应明确报告“已读取外来校验清单，尚未验证其与当前接收副本的对应关系”。不能使用 checksum verified 之类的措辞。

相同边界也需要覆盖 analysis-input。某个读取操作即使不叫 download，也可能造成数据内容物化。因而“工具没有云认证功能”并不足以证明它不会引发云端内容读取或水合。

建议明确默认范围：检查指定对象，采用与任务相称的读取深度，不改写输入，不自动补齐数据，不自动展开未授权的归档内容，也不因检查失败而升级为修复或重建。无法确定本地可用性的对象可以报告为未知，不应为消除未知而自动读取大量内容。

这不意味着每次正常结构读取都要单独征求许可，而是要避免把一个有限的检查请求扩展成没有边界的全量读取。用户明确请求传输时，可以交由已有传输工具处理所请求的范围，但不能顺带授权其他目录的下载、覆盖、修复或对外发信。

生成接收报告与修改输入数据也应分开：报告输出是检查结果，重写 H5AD、重排后重新导出、补矩阵或重算分割则是另一类动作。

此外，这两个技能会读取外来文档和清单。需要一条很小但重要的规则：清单、README、文件名和元数据都是待解释的数据，不是执行指令或授权来源。它们不能自行授权运行命令、发送邮件、下载内容或更换检查范围。这不要求建设大型安全框架，只要求不混淆数据与控制指令。

五、helper 的判断：有条件值得做，但不能成为第二个产品

我不认为 helper 是重命名的前置条件，也不认为首版必须包含 hashing、archive inspection 或 cloud adapters。

但如果 intake 要对大量路径作可重复的精确比较，而运行环境没有可靠的现成枚举与比较能力，那么一个小型 helper 有实际价值。不能一边推迟全部机械核验工具，一边让模型凭长清单的文字阅读声称完成逐路径全量验证。

因此，我的建议是：先确定证据和结论契约，再检查是否已有可复用能力；没有时，首版只做 scan 和 compare。不要为了“以后可能需要”同时加入哈希、云认证、传输、矩阵读取、自动修复或递归解包。

若 helper 进入首版，下列行为应属于最低要求，而不是后续优化：

保留精确相对路径和对象类型；对普通文件比较尺寸；默认不跟随符号链接，并记录链接对象；对无法枚举的部分保留错误和 partial 状态；不能把失败后的空列表当成空目录。外部清单中越界路径、重复且冲突的条目等问题，应显式拒绝或标为不可比较，而不是静默清洗。

“拒绝静默部分枚举”不应理解为一遇错误就丢弃所有结果。更好的行为是保留已取得的证据，同时让调用方明确区分“枚举完整且有差异”“枚举不完整”和“运行失败”。否则上层技能很容易把 partial 当成 clean。

提供一种稳定、可机器读取的证据格式就够了。首版不需要同时支持多种输出协议、数据库、插件系统或复杂配置语言。

云占位状态尤其不应过度承诺。一个跨平台标准库 helper 不应宣称能可靠识别任意同步系统的本地可用性。可以在有可靠证据时报告状态，没有时报告 unknown。相比为消除所有 unknown 而接入多种云服务，这更符合首版范围。

六、必须修正：重命名要决定行为兼容，而不仅是名称兼容

提案的迁移顺序总体合理，尤其是不改 compute environments 和历史结果目录，以及先验证新资源解析再撤下旧注册。但“创建新 canonical skill 并保留现有行为”需要加一个前提：现有行为已经符合新的职责边界。

如果旧 xenium-input-check 混有收件、传输、自动补件或其他越界行为，就不能为了声称兼容而全部带入 xenium-analysis-input-check。应先区分必须保持的行为和有意改变的行为，并把后者写入测试与迁移说明。

旧调用如何处理，也应在迁移前决定，而不是把“如果有真实消费者”留成一句开放条件。

在可检查、受控的调用范围内没有兼容需求时，干净迁移可以成立。不必为一个无人使用的旧名称保留永久入口。但“没有发现消费者”需要附带检查范围，不能等同于证明不存在任何消费者。

存在实际兼容需求时，最小 forwarding entry 是合理选择。它应转发至 canonical 实现，不拥有第二份检查逻辑，也不扩大权限、丢弃参数或导致重复执行。旧入口也不应在技能发现与路由中表现为另一个同等独立的技能，从而重新引入选择歧义。

还要区分名称兼容和资源依赖兼容。旧名称能够被调用，不代表文档引用、资源加载或其他直接依赖都已经迁移成功。测试必须实际验证资源解析，而不是只检查注册项存在。

若旧 generic 名称承诺的行为本来比新的 analysis-input 更宽，不能默认把所有旧请求机械转发过去后仍声称完全兼容。此时需要明确说明行为变化，或者对不再适用的请求给出清晰指向，而不是悄悄改变任务含义。

authoring 与 deployment 的分离应保留。修改技能定义和测试，并不自动包含修改运行中的注册、路由或部署状态。旧入口最终是被撤下还是保留为兼容转发，也应与已决定的策略一致，不能在不同步骤中作出相互矛盾的处理。

七、必须修正：把验收例子变成可以判定对错的断言

现有例子覆盖方向很好，但大多还是场景描述。每个关键测试至少需要说明：给定的范围和证据是什么、预期结论是什么，以及哪些动作绝不能发生。最后这一项很重要，因为报告措辞正确，不代表背后没有发生未授权扫描或下载。

我会优先补强以下几组测试，而不是扩大到大量真实格式和版本。

范围与权威测试：同一个 curated H5AD，在明确约定只交付它时，不因缺少 native images 被判交付不完整；在范围不明时，只能得到有限清点结论；在约定还包含其他对象时，则不能被当成完整交付。文档与约定冲突时，应保留冲突而非默选一个。

覆盖与结论测试：源或目标只有部分枚举时，缺失和额外项的措辞必须受影响；读取失败得到零条记录不能判为空目录；扫描器跳过的目录不能被当作已核验。相同路径、相同尺寸但内容不同的测试夹具，在没有 hashing 请求时，不要求技能发现字节差异，而要求它绝不宣称内容一致。

表示与对应测试：存在 H5 候选但内部没有相关表达矩阵时，不能用它消除信息缺口；标签文件不能代替矩阵；QC mask 不能代替 morphology image。ID 集合相同但顺序不同、数量相同但 ID 不同、以及不同 specimen 中标识符重复，应产生不同结论，不能统称 join 失败。

分析边界测试：缺少原始计数不必使所有表达探索都失败，但不能宣称支持要求原始计数的工作。没有图像不必阻塞所有空间检查，坐标参考信息不足也不能凭猜测补齐。部分输入有效时，应保留对该部分的有用结论，而不是只输出全包失败。

权限与失败模式测试：提供 sender checksum manifest 后，不发生本地摘要计算；占位对象不会被自动批量水合；检查失败不会触发修复、重建或发信。若实现 helper，还应验证符号链接、越界路径、类型冲突及归档不透明策略。输入文档中的操作指令不得改变权限。

迁移测试：新入口不但能被发现，还能加载正确资源并到达正确行为；保留的旧入口与 canonical 实现保持约定的结果和权限一致；移除旧入口时，不能留下看似迁移成功、实际运行仍依赖旧资源的情况。

其中，原来的第一条验收建议直接改写为：

“当交付约定明确限定为该 curated H5AD 时，不因缺少 upstream native outputs 判交付不完整；其结构有效性、数值含义及对具体工作的支持程度由 analysis-input 独立判断。”

这比“curated H5AD remains a valid delivery”更准确，因为 curated、扩展名正确和文件存在，都不应成为内容有效性的自动保证。

八、哪些是可选改进，哪些只会增加复杂度

可选而有价值的改进，是稳定的机器可读报告、小规模文件角色注释复用，以及有限的下游能力标签。它们应服务于已经出现的重复使用需求，而不是成为首版的架构前提。

不建议首版引入完整的 native 输出版本规则库、自动发现并补齐上游数据、统一 analysis-readiness 总分、强制完整分析计划、递归归档处理、多云认证与同步，以及永久维护两套名称对应的独立逻辑。它们要么改变了职责边界，要么把“有条件检查”错误地变成“承诺全面保证”。

也不必为了两项技能建立第三个调度技能、通用工作流平台或大型共享状态模型。两者共享少量证据定义即可；独立可调用不要求零代码复用，共享代码也不意味着必须形成先 intake、后 analysis 的强制流水线。

最后，没有 hashing 不是首版不合格的理由；没有 source manifest 也不是不能开始检查的理由。真正不合格的是把没有覆盖、没有执行或没有依据的部分写成已完成。

建议的实施路径是：先补齐范围与证据契约、第二个技能的最低流程及关键反例；再完成 canonical 名称和明确的旧入口策略；最后根据现有枚举能力决定是否加入最小 scan/compare helper。部署仍单独处理。

因此，我支持的是“完成上述必要修订后的受限首版”，而不是原方案无条件落地。最需要收紧的三个词是“完整”“一致”和“可分析”：每次使用，都应说明相对于什么约定、覆盖了什么证据，以及在哪些条件下成立。
